# Admin API and screens, source grants, ready to turn on: implementation plan (part 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Administrators manage virtual accounts (password, keys, admin flag, per machine `runAs` and folder grants), give accounts network sources, see every signed-in session and end it, and forget passwords saved with sign-in off. Every change to an account ends its sessions, streams and jobs. A virtual account opens each machine at its first granted folder. After this part, the docs no longer say sign-in is "not ready to turn on".

**Architecture:** A new hub router, `auth/admin-routes.ts`, under `/api/admin/`, behind a gate that checks on every call that the caller is an administrator with a session, and an audit line for every call (GET too). Changes go through the account store and then through one hub function, `accountChanged`, which raises the epoch (`Sessions.endAll`: sessions and streams end), cancels the account's hub jobs and compares, and asks each machine, as the account at its new epoch, to cancel its jobs there (the raised epoch also stops its workers). Source grants are a new table in the auth database. The hub checks them on every call to a source, inside the source's `Target`, so hub jobs and transfers are covered too. The web app gets an "Accounts" view, opened from the account menu.

**Tech Stack:** Node 22, TypeScript, Hono, `node:sqlite`, `node:test`; React 19, Playwright and axe-core for the browser checks.

**Spec:** `docs/superpowers/specs/2026-11-17-authentication-design.md` ("Accounts and identity", "Network sources", "Revocation takes effect at once", "Admin screens (web)", "Order of work" steps 3 and 4). Needs parts 1, 2a and 2b (`docs/superpowers/plans/2026-11-17-auth-1-hub-sign-in.md`, `2026-11-17-auth-2-agent-workers.md`, `2026-11-17-auth-2-agent-workers-2b.md`), all built on this branch. Board row 20.159. The release itself stays row 20.160.

**State before this part:** no `/api/admin/` route exists. Accounts are made only by `FILEDECK_BOOTSTRAP_ADMIN_FILE`. `Accounts` has `create`, `get`, `addKey`, `keys`, `bumpEpoch`, `epochOf` and `identity`, and nothing to list, change or delete. `Sessions.endAll` exists but nothing calls it. An epoch rise cancels no hub job. `mayUse` in `hub.ts` lets every signed-in account use every network source. The web app opens every machine at `/`.

## Decisions the spec leaves open

1. **Every change ends the account's sessions, also the caller's own.** The spec raises the epoch when a password, key or grant changes, and the epoch ends sessions. So an administrator who changes their own account is signed out too. The editor warns before it saves. A source grant given to a system user also ends that user's sessions.
2. **Ending one session** (one row in "Signed in") removes that row and ends its streams. It does not raise the epoch or cancel jobs, because jobs belong to the account, not the session. "End all sessions" for an account raises the epoch and cancels its jobs.
3. **Source grants cover a whole source**, read-only or read-write. Read-only allows `GET` and `HEAD` only (every source route that changes something uses another method). Administrators (system and virtual) can use every source read-write without a grant, because they already control every account and grant; act as root changes nothing for sources (sources are not machine accounts).
4. **The last administrator.** System administrators come from `FILEDECK_ADMINS`, which the screens cannot change. So the rule applies only when `FILEDECK_ADMINS` is empty: a change may not leave no virtual administrator who can sign in (one with a password or a key).
5. **Deleted names keep their epoch.** Agents remember the highest epoch per `kind:name`. A name made again would start at 0 and every agent would answer `account changed`. So a deleted account leaves its epoch in `retired_accounts`, and a new account of that name starts above it.
6. **A machine entry needs at least one grant**, and the grants keep the order the administrator gives. The first one is the folder the web app opens.
7. **Passwords**: 12 to 1024 characters. A virtual account may have no password and no key: it then cannot sign in, and the list says so.
8. **Name checks against system users**: the hub asks every machine (`/api/auth/lookup`, 2 s). A `true` refuses the name. A machine that does not answer does not block it (the spec: "a clash it can see"). A `runAs` that a machine says does not exist (or is uid 0 there) is refused; no answer allows it.
9. **The folder picker** browses the machine as the administrator. When the administrator cannot list a folder, the path can be typed. The hub checks the form of the path, not that it exists.
10. **Session ids shown to administrators** are derived from the stored key (`sha256("filedeck-session-id-v1:" + key)`, first 32 hex characters), never the key itself. The client address at sign-in is stored with the session, to show who is signed in from where.
11. **Passwords saved with sign-in off** are forgotten through an admin route and a button in the Accounts view. The hub logs their number at start while sign-in is on. No CLI step.

## Global Constraints

- Everything new is inert unless `FILEDECK_AUTH=on`. With it off, `/api/admin/*` answers 404 and `/api/nodes` is unchanged.
- Every `/api/admin/` route answers only a caller with a session (not the `du` API token) who is an administrator at that moment: a system user in `FILEDECK_ADMINS`, or a virtual account whose stored `admin` flag is true. Anyone else gets 403 `{"error":"administrators only"}`. The check reads the store on every call.
- Every `/api/admin/` call writes one audit line, whatever its method, with `user`, method, route, status and a cleaned body. A password, password hash or public key text never appears in an audit line, a log line, an error body or any response. Keys appear only as their fingerprint (`SHA256:` and unpadded base64, as OpenSSH prints it).
- No response holds a password hash. Accounts show `hasPassword: boolean`.
- Any change to an account (password, keys, admin flag, machines, grants, sources, deletion, "end all sessions") goes through `accountChanged`: epoch raised, sessions and streams ended, hub jobs and compares cancelled, agent jobs cancelled.
- Names: virtual `^[a-z_][a-z0-9_.-]{0,31}$`, never `root`, never a name in `FILEDECK_ADMINS`. System names and `runAs`: `validSystemName`, never `root`.
- Grant paths: absolute, at most 4096 characters, no NUL, no `..`; `//`, `.` and a trailing `/` are cleaned away; no segment may be a reserved name (`isReservedName`: `.filedeck-trash`, `.filedeck-work`, `.filedeck-work-*`). At most 64 grants per machine and 32 keys per account.
- Run server tests with a private `TMPDIR` (a folder only you can change). British English. No real infrastructure names in code, tests or docs; `npm run check:neutral` passes.

## Review Focus

1. **A name deleted and made again.** The new account must work on every agent at once (no `account changed`), and must not inherit saved passwords, keys or source grants. Test owners: Task 1 `retired epoch`, Task 5 `re-created name starts clean`.
2. **Two administrators removing the last two virtual administrators at the same moment.** Exactly one change may succeed. The check and the write run with no `await` between them. Test owner: Task 5 `last admin, at once`.
3. **An administrator whose flag is removed while their page is open.** Their next admin call gets 403, without signing in again. Test owner: Task 4 `admin checked on every call`.
4. **A paused or queued hub job of a changed account, held by the other hub of a rollout** (a row in the shared job store). It must end as `canceled`, not run later as the old epoch and fail. Test owner: Task 3 `stored and paused jobs`.
5. **A read-only source grant used through a hub job or a transfer**, not only through the proxy. The write must fail with 403 and nothing may be written. Test owner: Task 6 `read-only through a job`.
