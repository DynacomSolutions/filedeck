# Sandbox and safe file placement

## Sandbox

Repositories and archives are other people's data, so the helper programs the agent runs on them go through a small launcher, `filedeck-sandbox` (built from `server/native`, installed beside `filedeck-fanwatch` in the image; `FILEDECK_SANDBOX_HELPER` names it, and when it is not set the agent uses `/usr/local/bin/filedeck-sandbox`, then the copy `npm run build` compiled into `server/dist/native`, never one found through `PATH`). That is every Git command (status, details, diffs) and every start of `bsdtar` and `7zz` (compress, extract, list, password check, zip download). The launcher drops privileges, clears every capability (see below), sets no-new-privileges and applies a Linux Landlock ruleset that handles every right the running kernel offers: the program can read files beneath the served folder and the system folders it needs to start, nothing else, and it can write nothing at all. A link inside a repository that leads outside the served folder therefore fails when Git opens it. On kernels with Landlock ABI 4 or newer TCP bind and connect are denied too, with ABI 6 or newer so are abstract unix sockets and signals to other processes; an older kernel simply lacks those rows. On every kernel the launcher also installs a seccomp filter that makes `socket()`, `socketpair()`, `connect()`, `bind()`, `listen()`, `accept()` and io_uring fail, so a confined program can reach neither UDP nor a pathname unix socket under the served folder (x32 system calls end the process); it uses only the descriptors it was given. The same filter refuses, for every confined program, `mount` and the new mount calls, `umount2`, `pivot_root`, `chroot`, the `setuid` and `setgid` families, `capset`, `ptrace`, `process_vm_readv` and `process_vm_writev`, `kexec_load`, `bpf`, `unshare`, `setns`, `mknod` and `mknodat`, `clone3` (answered with "not implemented", so the C library falls back to `clone`) and `clone` with a new-namespace flag, and, unless the caller allows them, the calls that change metadata: `chmod`, `fchmod`, `fchmodat`, `fchmodat2`, `chown`, `fchown`, `lchown`, `fchownat`, `utime`, `utimes`, `utimensat`, `futimesat` and the `setxattr` and `removexattr` families (Landlock does not restrict these). Only extraction by 7-Zip is allowed the metadata calls, because it sets modes and times on what it creates in its private staging folder; compression, listing, zip download, `bsdtar` and Git need none. This layer is best effort (x86-64 and arm64, kernels with seccomp filters); the agent logs the sandbox state at start-up (Landlock ABI, handled rights, whether the socket filter is on) and `/api/info` shows a summary under `sandbox` (the table is in `server/native/filedeck-sandbox.c`). No confined program keeps a Linux capability: the launcher empties the permitted, effective, inheritable, ambient and (where it may) bounding sets, also for a program that stays uid 0, so a program that is taken over cannot change the owner, mode or times of files outside its grants, mount, or read what the file modes forbid. The launcher checks that the sets are exactly what was asked, and shrinks the bounding set as far as it may: the chart does not grant `SETPCAP`, so there it stays as it is, which does not matter, because no-new-privileges (set before the program starts) stops the exec from raising the permitted set above what the process holds, which is nothing. The one exception is named by the caller: `dac_read_search` (read any file and search any folder by mode, still limited by Landlock to the granted folders), which the launcher keeps across the change of user; where the container does not hold it (the usual container defaults do not, but do hold `dac_override`) the tool is given `dac_override` instead, which also bypasses write permission checks, with Landlock still limiting writes to the granted writable folders. If the agent holds neither read capability (it is not root, or its container dropped both), the tool runs as the agent's own user with no capabilities instead, and 7-Zip extraction of an archive that user cannot read is refused with a clear message (it needs the metadata calls, which are never combined with uid 0 without a capability set: with neither capability the tool would be the agent itself, which owns root's files; a default chart install holds the read-search capability, a plain container the override one, so both keep working). The agent logs the choice, and at start-up starts a harmless program as every identity with its real capabilities and logs one line saying that each identity starts or which cannot (`archive tools and git, identities: ...`); `--probe` reports whether capability handling works. Git's own error text is never sent to a client: failures are answered with fixed messages and the details stay in the agent's log.

`FILEDECK_SANDBOX` says what happens when Landlock is not usable (kernel older than 5.13, Landlock not enabled, or blocked by the container's seccomp profile):

- `require`: without Landlock the features that start helper programs answer a 503 error. **This is the default in the container image and in the chart** (`agent.sandbox`).
- `auto` (the default only for a plain development start, outside the image): Landlock when present. Without it Git still runs, but only for a repository whose git directory holds no symbolic link at any depth and no `include` or `includeIf` setting (at most 50,000 entries are checked; more is a refusal; the check is repeated before every Git command), and never as root. This is a weaker guarantee than Landlock: a link created between the check and Git's read is not stopped. The agent logs once at start-up that the sandbox is unavailable.
- `off`: no launcher and no extra checks, only the path checks in `server/src/git.ts`. For development.

What the archive tools may touch, with the sandbox in force (everything not listed, in particular everything else below the served folder, is closed to them by the kernel; the rules are attached to descriptors the agent holds, so renaming or replacing a name while a tool runs changes nothing, and a tool's working folder is passed to the launcher as a descriptor, never as a `/proc/self/fd` path):

| Tool start | Reads | Writes | Runs as (agent is root) |
|---|---|---|---|
| Compress, `bsdtar` | up to 4,000 selected items: each on its own, opened path-only; the folder holding the selection and its unselected siblings are closed. A selected link is stored as itself and needs no grant. **Above 4,000 items (the limit for one job or download is 10,000, for every route alike) the pinned source folder is granted instead**: bsdtar is still told the names explicitly and stores links as links, so only the selection is archived, but it *can* read unselected siblings; only the exclude patterns keep Filedeck's own folders out | a private scratch folder only: the archive being written (by name) and the temporary file the 7z writer keeps | the selected folder's owner (groups cleared); for a root-owned folder the archive tools' user with the read-search capability |
| Compress, 7-Zip | **the whole pinned source folder**, whatever the count: 7-Zip lists its working folder to find the names it is given, and with absolute paths or a list file it lists their parent instead (tried with the real tool: both fail without read access to that folder). It is told only the selected names, so it archives only those, but it *can* read every unselected sibling and everything else beneath that folder; only the exclude patterns keep Filedeck's own folders out | one private folder only (it writes by name): the archive being written and the exclude list | the selected folder's owner; for a root-owned folder the archive tools' user with the read-search capability |
| Zip download, `bsdtar` | as for compress with `bsdtar`: each selected entry up to 4,000, the pinned folder above; started in the pinned folder by descriptor | nothing (the zip goes to a pipe) | the folder's owner; for a root-owned folder the archive tools' user with the read-search capability |
| Extract, `bsdtar` | nothing below the served folder: the archive arrives on standard input | nothing (the tar stream goes to a pipe) | the archive tools' user |
| Extract, 7-Zip, one archive | the archive as an open read-only descriptor (read as `/dev/fd/3`), plus the kernel rule on that same file | the private staging folder only (owned by the tool user for the run) | the archive tools' user when it can read the archive by the file's own mode (opening `/dev/fd/3` checks the file's permissions again: a 0600 archive gave "Permission denied" in CI; the folders above the archive do not matter for a descriptor), else that user with the read-search capability |
| Extract, 7-Zip, split set | its own private copies of the checked parts, in a reserved folder inside the agent's private work folder (read through the rule on that folder) | the private staging folder only (the copies are removed with the job) | the archive tools' user with the read-search capability: 7-Zip makes a relative name absolute with `getcwd()`, and the agent's work folders above the copies are mode 0700, which the unprivileged user cannot traverse without it ("Permission denied" in CI) |
| List and password check, 7-Zip, one archive | the same open descriptor | nothing | as for extraction of one archive |
| List and password check, 7-Zip, split set | with Landlock: each part opened by name, one rule per part (at most 4,094 parts: the launcher takes 4,096 grants in all, and `/dev/urandom` and an absolute 7-Zip path each take one; 4,095 when 7-Zip is found by name); in `off` and fallback: the parts opened by name after the agent checked them (7-Zip finds the next part by changing the name, so a descriptor alone cannot work: "Cannot open the file as archive"; there is no kernel rule to hold the parts there, a weaker guarantee in modes where the tool is unconfined anyway) | nothing | the archive tools' user when it can read the first part and the folders above it by mode, else that user with the read-search capability |
| List, `bsdtar` | nothing below the served folder: the archive on standard input | nothing | the archive tools' user |

The archive tools' user is its own: a fixed uid and gid with no account needed (default 65533 for both; `FILEDECK_ARCHIVE_UID` and `FILEDECK_ARCHIVE_GID` change them; 0 is refused), different from the user the media tools use (65534), so a compromised media tool, which runs outside these sandbox domains, cannot signal or trace an archive tool on kernels without the newest Landlock scopes, nor reach its staging. Archive tool processes that serve interactive requests are bounded by two pools, so that neither can starve the other or the jobs: zip downloads (`FILEDECK_ZIP_DOWNLOADS` in all, default 16; at most 8 for one client; 8 more may wait up to 5 seconds) and listings and password checks (8 in all, 4 for one client). A client over its own limit is refused at once with a 429 that says so, and only that client; a full pool answers "busy" after the short wait. The client is the address the server itself observed (the hub's `x-filedeck-client` when the agent token is set, as for searches). The per-client limits need the agent token (chart: `agentToken.generate`, which creates the shared hub-to-agent Secret, or `agentToken.secretName`): without it the agent cannot tell the hub from a direct client and every user behind the hub shares one key, so the per-client limit is not applied and only the pool's own limit holds (16 downloads, 8 listings), with a "busy" answer when it is full. Compression and extraction jobs are not in these pools: they wait in the job queue with its own concurrency and never fail for lack of a slot. A zip download whose body is not read for 60 seconds is ended and gives its slot back. The agent lets go of its own descriptors for the selected items as soon as the tool has started (the tool and the launcher hold their own copies); if the process cannot hold that many descriptors it grants the whole source folder instead, and logs it. A failure to list or password-check a split set is reported as an error and never skips the check.

Without Landlock (`off`, or `auto` where Landlock is unusable) there are no read or write rules at all; the tools differ only in how they reach the archive and who they run as: `bsdtar` reads the archive from standard input as before, and 7-Zip is handed a single archive as an inherited descriptor (kept open through the launcher with `--keep-fd`, read as `/dev/fd/3`), never by a name that could be swapped after it was checked. The user change and the working folder by descriptor go through the launcher in those modes too when it is installed, and every other descriptor above 2 is closed for the tool.

An archive is other people's data and the tools that parse it need no identity of their own, which is why they run as the archive tools' user. The agent opens the archive, and each part of a split set, without following links and without waiting on a pipe, and takes the produced archive out of the private folder through descriptors, with a size bound (see [Archives and passwords](archives-and-passwords.md)). A launcher failure (too many folders, a step that failed, Landlock gone) is reported as an error ("the sandbox could not start the archive tool", the detail in the agent's log) and is never answered by trying another tool. Folders of Filedeck's own (the trash store, work and staging folders) found inside a selected entry are kept out of an archive by the tools' exclude patterns, not by the kernel: Landlock allows by hierarchy and cannot take a folder out of a granted tree. For `bsdtar` the patterns include the staging prefix, so such a folder that appears after the scan is left out too. For 7-Zip, whose wildcard matching stays off (so that names such as `a?b.txt` work), the exact names `.filedeck-trash` and `.filedeck-work` are excluded by name at any depth, and staging-prefix folders by the exact paths the scan found; a staging-prefix folder created inside a selected entry after the scan can be read by 7-Zip (it is private to the agent that made it, so a tool running as the selection's owner cannot read it either; for a root-owned selection the tool holds the read-search capability, so its content is readable there). With `FILEDECK_SANDBOX=require` and no usable Landlock the archive features answer the same 503 as Git; with `auto` and no Landlock they run with the path checks described in [Archives and passwords](archives-and-passwords.md).

Who runs as what, stated once: no archive tool runs as root, except in one case: when the agent is root and holds neither read capability, compression, zip download and listing of content only root can read run as uid 0, with every capability cleared by the launcher, the metadata calls filtered and Landlock confining them (7-Zip extraction is refused there). Git runs as root, with every capability cleared, only for a root-owned repository that the unprivileged user cannot read (Git checks access with `access(2)`, which ignores capabilities for any other user). No confined program keeps root's capabilities.

What the sandbox restricts: file access by Landlock (reads, writes, creating, removing, renaming and linking, executing, and on newer kernels sockets and signals), every capability, sockets, the privilege and namespace calls and (except for 7-Zip extraction) the metadata calls listed above. What it does not restrict:
- Tools that may read a whole folder: 7-Zip compression always reads the whole pinned source folder, and `bsdtar` for compression and zip download does so above 4,000 selected items (below that each selected item is its own grant).
- Concurrent 7-Zip extractions run as the same archive user and are allowed the metadata calls, so a tool that knew the path of another job's staging folder (random, under the agent's private work folder, not listable, but searchable with the read capability) could change modes and times of its files; it cannot read or write them beyond what Landlock grants. A per-job user would close it and needs per-job accounts or an id range, which is not done here.
- Anything the tool's own user may already do: 7-Zip extraction may change the metadata of files that user owns (its staging folder, nothing else is owned by it) because it is allowed the metadata calls.
- In `off` mode (and in `auto` when Landlock is not usable) every tool runs without kernel confinement: git, `bsdtar` and `7zz` have only the agent's own path checks and the privilege drop (when the launcher is installed and starts the tool, which it does whenever a user or a working folder is given, capabilities and the filter above apply in these modes too; with no launcher nothing does). The start-up log says so in a line, and `/api/info` shows `sandbox.archiveTools` as `confined`, `unconfined` or `disabled`. "No launcher" can only happen in a development start without the helper built or installed (`FILEDECK_SANDBOX_HELPER` missing, or `FILEDECK_SANDBOX=off`); the image always ships it. Then the working folder is given by its current path and the user change is Node's own: Node's process start (libuv) calls `setgroups(0)` whenever it is given a gid, so the supplementary groups are cleared there as well (a root-only test checks `id -G` in each mode).
- The `7zz --help` probe at start-up, which touches no archive and runs unconfined.
- The `rm -rf` that removes a user's tool-output folder after a compression run as that user: it runs as that user, on that one folder, unconfined (no launcher, so it also keeps whatever the agent's children inherit; it holds no capability because the user change drops them).
- What an older kernel's Landlock lacks (the table in `server/native/filedeck-sandbox.c`): below ABI 2 renames across folders are not controlled, below 3 truncation, below 4 the network, below 5 device ioctls, below 6 abstract unix sockets and signals, below 9 pathname unix sockets; the launcher's seccomp filter covers the sockets on the architectures that have it. Landlock never restricts a descriptor a process already holds, which is why the tools are handed only the descriptors they should use.
- A folder inside a granted selected entry (see above). The media tools' user (65534) is shared by other helper programs, which can reach files it owns; the archive tools use their own user (65533), whose files are only its private staging folder while a tool runs.

Who Git runs as when the agent runs as root: the owner of the git directory; for a root-owned git directory the unprivileged user the media tools use (uid and gid 65534) when that user can read it; a root-owned repository that user cannot read runs as the agent's own user with every capability cleared (and is refused in the `auto` fallback): the launcher removes root's capabilities, and Git reads the repository as its owner. (A read capability handed to the unprivileged user does not work for Git, which checks access with `access(2)`, and that call ignores capabilities for any user but root.) An agent that does not run as root changes nothing. When the served root is the whole machine, the system and process folders are inside it, and Landlock cannot take folders out of an allowed tree: a root-owned repository that the unprivileged user cannot read, served that way, can still read them through a hostile repository, but only someone who could already write a root-owned repository there can create one. For such a deployment serve a narrower root, or keep repositories readable by the unprivileged user so that they run unprivileged.

## Move and copy without overwrite

A move or copy without overwrite never replaces what is at the destination, also when something appears there after the check. A file is placed with `link` and `unlink`, which is exact. A folder, and a file on a filesystem without hard links, is placed by a small helper, `filedeck-rename` (built from `server/native`, installed in the image; `FILEDECK_RENAME_HELPER` names it, and when it is not set the agent uses `/usr/local/bin/filedeck-rename`, then the copy `npm run build` compiled into `server/dist/native`, never one found through `PATH`). It calls `renameat2` with `RENAME_NOREPLACE` on the descriptors of the two parent folders, which the agent holds open, and is started once per placed item, directly by the agent (not through the sandbox launcher), with an empty environment and no other descriptor (it closes any that the agent itself was started with). Where the helper is missing (the agent says so in one line at start-up), or the filesystem or kernel does not have the flag, the agent checks and then renames as before, and one window remains: an empty folder created at the destination between the two steps is replaced (on a filesystem without hard links, a file created there in that instant as well). Nothing else can be lost.

## Sign-in and sessions

Sign-in is built in three parts. Part 1 gives accounts, sessions and the sign-in screen on the hub, a signed user on every call to an agent, and the account in the audit log. Part 2 comes in two steps: the first, in this version, runs every signed-in request on an agent in a worker process that holds the person's own user (see [Workers on the agents](#workers-on-the-agents)); the second adds system sign-in (PAM and `authorized_keys`). Part 3 adds the screens for accounts and grants. Sign-in is off by default (`FILEDECK_AUTH`, see [Configuration](configuration.md)). With it off, these are the only changes from a version without sign-in: `GET /api/auth/me` answers `{"auth":false}`; the web app waits for that answer before it first draws; the agent keeps its own index and folder-size files (`index-<node>.db`, `sizes-<node>.db` and their `-wal`, `-shm` and journal files) at mode 0600, and changes those an older version left to 0600; a trash item's `meta.json` is read only when it is a regular file of at most 1 MiB and not a link (else the item is listed under its id, and it can be deleted but not restored); a value of `FILEDECK_MAX_WORKERS` or `FILEDECK_WORKER_IDLE_SECONDS` that is not a whole number of at least 1 stops the start; and the trash also lists the account folders (`u<uid>`, `v-<name>`) that sign-in left on a volume (see Trash with sign-in on, below). Every other response is as before. **`FILEDECK_AUTH=on` is not ready to turn on.** System accounts cannot sign in until the second step of part 2, there is no screen yet to make accounts or to give them machines and folders, and network sources are open to every signed-in account until part 3 adds grants for them.

Who can sign in in this part: only virtual accounts (accounts kept on the hub), and the only way to make one is `FILEDECK_BOOTSTRAP_ADMIN_FILE`, which makes the first administrator. There is no route or screen yet that makes accounts, gives an account machines or adds keys (part 3). The first administrator has no machines, so it sees no machine, only the network sources, and every job. System accounts cannot sign in yet: their password is checked by PAM and their key against `authorized_keys` on an agent, which comes with the second step of part 2. Until then every name that is not a virtual account fails as a wrong password does, and the password is still hashed once, so the answer takes as long. The name `root` is refused before any check. On the agents, an account whose name (or, for a virtual account, whose `runAs` user) resolves to uid 0 or gid 0 is answered as an unknown name: 403 `{"error":"no account on this machine"}`. A system account reaches an agent today only through the `filedeck du` token (`FILEDECK_API_TOKEN_ACCOUNT`).

What answers without a session: `GET` and `HEAD` of every path outside `/api/` (the web app and its files for any URL, so a deep link still loads, and `/healthz`), and the sign-in routes `/api/auth/me`, `/api/auth/login`, `/api/auth/challenge`, `/api/auth/login-key` and `/api/auth/logout`. A request with the `filedeck du` token is checked first and acts as `FILEDECK_API_TOKEN_ACCOUNT`. Every other request under `/api/` answers 401 `{"error":"signed out"}` with the header `X-Filedeck-Auth: signed-out`. The web app then shows the sign-in screen; when the same account signs in again the app goes on where it was, with unsaved editor text kept, and another account gets a fresh page. An event stream opened before sign-out or before the session ended keeps running until it closes, and a 401 on an event stream does not bring up the sign-in screen (part 2 changes both). State-changing requests keep the origin checks of the request guard; there is no separate CSRF token, because `SameSite=Lax` and those checks cover it.

The session cookie is `__Host-filedeck` with `Secure`, `HttpOnly`, `SameSite=Lax` and `Path=/`, and its value is 32 random bytes as base64url. The hub keeps only the SHA-256 of the value, with the account, the time of sign-in and the last use, in the SQLite file of `FILEDECK_AUTH_FILE` (mode 0600), so a copy of that file cannot be used to sign in. A session ends after `FILEDECK_SESSION_IDLE_SECONDS` without use (default 8 hours), `FILEDECK_SESSION_MAX_SECONDS` after sign-in (default 7 days), at sign-out, when its virtual account no longer exists, or when the account's epoch (a counter per account) is raised. A new sign-in in the same browser removes the session it had before.

Sign-in needs HTTPS: on plain HTTP the routes that sign in (`login`, `challenge` and `login-key`) answer 403 `{"error":"sign-in needs HTTPS"}`. A request counts as HTTPS when its connection is TLS, or, with `FILEDECK_TRUSTED_PROXIES` above 0, when the last `X-Forwarded-Proto` value is `https`. Only with `FILEDECK_TRUSTED_PROXIES` at 0 may a client on a loopback address sign in on plain HTTP; behind a proxy the loopback peer is the proxy, which may sit on the same host as the hub while the client does not. Browsers also offer WebCrypto, which key sign-in needs, and `__Host-` cookies only on HTTPS.

Password sign-in (`POST /api/auth/login` with `name` and `password`): a virtual account's password is stored as a scrypt hash (N = 2^15, r = 8, p = 1, a 16-byte random salt), made by `filedeck hash-password` for the first administrator. Every failed sign-in, by password or key, answers 401 `{"error":"sign-in failed"}`, the same for an unknown name, a wrong password, a bad key or a damaged request, and no failed answer (including the 429 of the limits below and the HTTPS 403 above) comes sooner than 500 ms after the request reached the hub.

Key sign-in: the browser asks for a challenge (`POST /api/auth/challenge` with `name`). A challenge is 32 random bytes, valid for 60 seconds, used once and bound to the name. When a sign-in request has a name and a challenge and is not stopped by the limits below, the hub takes (uses up) the challenge before any other check, so it is used up also when the public key or the signature is missing, when the name is `root`, and when the attempt fails for any other reason. The answer has the same form whether or not the name exists. One client address may ask for 20 challenges a minute (more answer 429 with `Retry-After`, which does not count as a failed sign-in); one client address holds at most 5 for one name (the oldest of these goes first, so one address cannot push out the challenges another address asked for), and the hub at most 10,000 in all. A name longer than 256 characters gets an answer, but nothing is kept. The browser signs four SSH-wire strings, `filedeck-login-v1`, the hub's id, the name and the challenge, and sends the public key and the signature to `POST /api/auth/login-key`. The hub accepts it when the challenge is live for that name, the public key is one stored for the virtual account and the signature verifies. Only `ssh-ed25519` and `ecdsa-sha2-nistp256` keys are accepted, and a key line with options before the key type is refused. In this part no route stores a key for an account, so key sign-in cannot succeed yet in a deployment.

The key file is read in the page and never leaves it: the hub gets only the public key line and the signature. The file must be an OpenSSH private key (`-----BEGIN OPENSSH PRIVATE KEY-----`) that holds one Ed25519 or ECDSA P-256 key. RSA keys are not supported yet, and a file with several keys is refused. For a protected key the page asks for the passphrase and decrypts the key with bcrypt-pbkdf (at most 1,024 rounds; `ssh-keygen` uses 16) and AES-256 in CTR mode (`aes256-ctr`, what `ssh-keygen` makes) or GCM (`aes256-gcm@openssh.com`); any other cipher is refused with "key encryption not supported".

Limits on failed sign-ins, kept per name and per client address (an IPv6 address counts by its /64): up to 5 failures in any minute get the normal answer, and the fifth also starts a block of 1 second, and each further failure blocks for twice as long as the one before, `2^(failures - 5)` seconds, at most 15 minutes. While a block lasts, sign-in answers 429 `{"error":"too many attempts"}` with `Retry-After`. The count goes back to zero after a minute without failures that follows the end of the block, so the blocks keep growing while the guessing goes on. An attempt is counted when it starts, so parallel guesses cannot all slip past the check. A good sign-in clears its name and takes back only its own count from the address, so one known account cannot clear the address for guesses at others. The hub keeps at most 10,000 names and addresses; above that it forgets, in this order, entries that have lapsed, entries that are not blocked (fewest failures and oldest first), then the oldest blocked ones.

Hub to agent: with `FILEDECK_AUTH=on` an agent answers every request except `/healthz` and `/metrics` with 401 `{"error":"no user"}` unless it carries a valid `X-Filedeck-User` header, and writes an audit line for the refusal without the header's value. The hub signs that header for each call: a small JSON object (kind, name, epoch, issue time, and for a virtual account the system user it runs as and its folder grants on that machine) with HMAC-SHA256 under a key derived from `FILEDECK_AGENT_TOKEN` by HKDF. The agent accepts it for 60 seconds after the issue time, and refuses one issued more than 5 seconds in the future. The hub drops any copy a client sends. The agent then runs the request as that account, in the account's worker (see [Workers on the agents](#workers-on-the-agents)). A virtual account may use only the machines it has access on: the others are left out of the machine list, and every request that names one, or names a machine that does not exist, answers 403 `{"error":"no access to this machine"}`, so a hidden machine's name stays hidden. This holds for every route that takes a machine name: the requests passed on to a machine (`/api/nodes/<machine>/...`, also those that use saved passwords), transfers, jobs, folder compares, and forgetting saved passwords (`POST /api/vault/forget`). A system account may use every machine in this part. Network sources are open to every signed-in account until part 3.

Jobs on the hub (copy, move, trash, delete and sync jobs, and folder compares) belong to the account that started them. Every step of a job runs as that account, also when another hub process takes the job over after a restart, and only that account and administrators see or steer the job: for every other account the job does not appear in the list, and every route on it answers 404 `{"error":"not found"}`. A job without an account (one started with sign-in off, or by an older version), seen with sign-in on, is shown to administrators only. A job keeps the identity it started with (the account, its epoch and its machine grants at that time): in part 1 a later change to the account, such as a raised epoch, changed grants or the removal of the account, does not stop a job that is already running or waiting. The jobs an agent runs itself (extract, compress, folder size, under the agent's `/api/jobs`) belong to the account that started them too (part 2): only that account sees them in the list, and for every other account each route on one answers 404 `{"error":"not found"}`. A size request for a folder that another account is already scanning joins that scan; the second account can follow that job, but it does not see the scan's current path, the job is not in its list, and it cannot cancel the job. Folder sizes (`/api/du` and the size job) follow the account as well. A virtual account gets sizes only for folders inside its grants: any other folder, also `/` or a folder that only leads to a grant, answers 403 `{"error":"outside your folders"}`, because its total would tell the size of everything else in it. An answer leaves out each folder that the account cannot open, and each file in such a folder; a request for such a folder answers 403 `{"error":"permission denied"}`. The total of a folder that a system account can open includes the folders below it that the account cannot open.

Saved passwords (the vault for encrypted archives and PDFs, see [Archives and passwords](archives-and-passwords.md)) belong to the account that saved them. With sign-in on, an account lists, uses, extends and forgets only its own: `GET /api/vault` lists them, `POST /api/vault/forget`, `DELETE /api/vault/<id>` and `DELETE /api/vault` remove only them, and a request passed on to a machine gets only the caller's own saved password. Administrators get no access to other accounts' passwords. A password saved with sign-in off has no account, and with sign-in on nobody uses it; it stays in the vault until it expires or is forgotten with sign-in off. An entry for a machine the account may no longer use is not listed. Turning sign-in off again makes every account's saved passwords usable by everyone who can reach the hub, as all passwords were before sign-in (for a path saved by several accounts, the most recently used entry wins). The first start of this version moves the vault file to a new layout (each entry gets an owner column). An older version can still read the moved file and use the passwords in it, but it cannot save a password in it any more: the save fails with an error. Keep a copy of the vault file if you may need to go back to an older version.

Audit: every audit line of a request with a known account names it in `user`, as `sys:<name>` or `virt:<name>`, on the hub and on the agent. The hub's refusal lines (cross-site, too large, wrong type, aborted) are written by the request guard before sign-in is checked, so they never carry a user; the agent's refusal lines do. A sign-in attempt is an ordinary audit line (with `user` only when the browser was already signed in): the route, the `name` from the body, the status and the client address. A password, private key, signature, challenge, session id or header MAC never appears in a log line, an audit line, a URL or an error body.

### Workers on the agents

With sign-in on, the agent's own process (root) keeps the routing, the check of the signed user, `/healthz`, `/metrics`, `/api/info`, the folder sizes (`/api/du` and the size jobs) and the trash sweep. Every other request runs in a worker: a Node process that the agent starts for the account through `filedeck-sandbox`, as the account's own uid, gid and supplementary groups. A system account is looked up by its name, a virtual account by its `runAs` user, on that machine. The worker holds no capability, has no-new-privileges set, and runs under the launcher's seccomp filter, which refuses network sockets (only a connected pair of unix stream sockets is allowed, for the pipes of the programs it starts). It gets no secret: no agent token, API token or vault key in its environment, its arguments or its start-up message. Its heap is at most 96 MiB (`--max-old-space-size=96`). The agent talks to it over a socket pair it made before the start (no path on disk); request and response bodies stream both ways, and a client that goes away stops the worker's work on that request.

- One worker per account: two virtual accounts with the same `runAs` user but different grants get separate workers. At most `FILEDECK_MAX_WORKERS` (default 6) run at once; when a new account needs one, the least recently used idle worker is stopped. When every worker is busy the answer is 503 `{"error":"too many people are using this machine; try again"}` with `Retry-After: 5`. A worker exits after `FILEDECK_WORKER_IDLE_SECONDS` (default 600) without use; one with a request in flight, an open stream (such as the event stream) or a running job is not idle.
- A worker that dies (out of memory, killed) ends its requests in flight with 503 `{"error":"worker stopped"}`, or, when the answer had already started, with a body that ends in an error. The next request starts a new worker. A worker that cannot start gives 503 `{"error":"worker failed to start"}`, and the same answer for the next 5 seconds. A failed account lookup gives 503 `{"error":"account lookup failed; try again"}`, never 403. An account with more than 256 groups is refused with 503 `{"error":"account has too many groups"}` (its groups are never cut). Group 0 is left out of a worker's groups, and the agent logs it.
- When the hub raises an account's epoch (see above), the agent stops that account's workers before it serves the request; a request with the older epoch then answers 401 `{"error":"account changed"}`.
- A system account's worker has no Landlock rules: the kernel's file modes for that user decide what it can read and change, as in a shell on that machine. The total of a folder size includes subfolders it cannot open (see the jobs paragraph above).
- A virtual account's worker also runs under Landlock: it can read below each of its grants, write only below grants with `write: true`, and use its own folders (temporary folder, thumbnails, index, trash folders) and the read-only files Node needs to run. This needs Landlock ABI 3 or newer (Linux 6.2); on an older kernel, or with the sandbox off, a virtual account's requests answer 503 `{"error":"virtual accounts need Landlock on this machine"}`, and the agent logs at start which ABI it found. Landlock does not cover every call (for example `chmod`, `chown` and `stat`), so the worker also checks every path a request names: a path outside the grants answers 403 `{"error":"outside your folders"}`, also `/` and a request that names no path; a change below a grant without `write` answers 403 `{"error":"read-only folder"}`. A link inside a grant that leads out of it is refused by the kernel, also for search, thumbnails, Git, archives and folder sizes. A grant that is a link, or runs through one, is left out, and so is a grant that does not exist; the agent logs each. The list of mounts (`/api/mounts`) shows only the mounts at or below a grant.
- Programs the worker starts (Git, bsdtar, 7-Zip, ffmpeg, qpdf) go through `filedeck-sandbox` as before, but they run as the worker's own user and can never get more than the worker has. The rules in [Sandbox](#sandbox) on who the archive tools and Git run as (uid 65533, 65534, the read capability) are for the agent's own process, with sign-in off. The limits on searches, archive tools, thumbnails and hashing that run at once apply to each worker.
- Each account has its own caches: thumbnails in `<FILEDECK_THUMB_DIR>/accounts/u<uid>` and the compare and listing index in `<FILEDECK_INDEX_DIR>/accounts/<account>`, both 0700 and owned by the account, so a cached file made from one person's view is never given to another. Accounts with one uid (a system account and the virtual accounts that run as it) share the thumbnail folder. Each thumbnail cache holds at most its share of `FILEDECK_THUMB_CACHE_MAX` (divided by `FILEDECK_MAX_WORKERS`, at least 16 MiB), and once no worker runs as its uid, the agent empties it as the account. Transcoding keeps nothing on disk. The agent's own index and folder-size files (`index-<node>.db`, `sizes-<node>.db`) are 0600, root's only. What an operator must set for these folders is in [Configuration](configuration.md).
- Jobs: archive jobs (compress, extract) and permission changes run in the account's worker. They are kept in the worker's memory only, so they are lost when the agent stops or restarts: they are not handed to the next agent process as with sign-in off, and asking for one afterwards answers 404. Folder-size jobs stay in the agent's own process and keep the hand-over. A virtual account's archive jobs build their result in the worker's temporary folder and then copy it into place, because `.filedeck-work` at the volume's root is outside its grants.

Account lookup: the agent asks the machine, not its own image, who an account is. A small helper in the image, `filedeck-id`, is opened by the launcher from the image and run by its descriptor (`--exec-outside`) inside the machine's root (`FILEDECK_ROOT`), with the machine's own libc and NSS (local files, LDAP or SSSD), as uid and gid 65534 and with no capability. Nothing is written on the machine, and nothing from the machine is loaded into the agent's process. For the change of root the agent container needs the `SYS_CHROOT` capability, which the chart adds only with sign-in on. When the helper cannot run there (a machine without glibc, for example), the agent logs `system accounts: host lookup unavailable (<reason>); only local /etc/passwd accounts resolve, and system sign-in is refused` and reads only the machine's `/etc/passwd` and `/etc/group`.

Trash with sign-in on: each volume's `.filedeck-trash` (root's, 0711) holds one folder per account: `u<uid>` for a system account and `v-<name>` for a virtual account (owned by its `runAs` user), each 0700. The agent's own process makes the folder the first time an account deletes something on that volume; the worker moves the item into it as the account, and the account lists, restores and empties only its own folder. Two virtual accounts with the same `runAs` user therefore do not see each other's deleted files. Items deleted before sign-in was turned on are moved into `u0` (root's, 0700) the first time an account folder is made on that volume: no account sees them with sign-in on, and with sign-in off they are listed as before (with ids `u0/<id>`). A virtual account has a trash only on volumes where one of its write grants lies; on a volume mounted inside a write grant, deleting to the trash answers 403 and the item must be deleted instead. The trash sweep runs as each folder's owner (root never walks or deletes inside an account's folder), and the size cap covers the whole volume. With sign-in off the agent lists every account's folder too. Restoring an account's item from there needs a target folder (403 otherwise), and is refused with 409 when it would need a copy (the target is on another mount, also another bind mount of the same filesystem), or, on a machine without a no-replace rename, when the item is a folder: restore it signed in as the account instead. With the sandbox off (`FILEDECK_SANDBOX=off` or no Landlock), a virtual account's trash folder is not swept (the agent logs it), and deleting from it or emptying it with sign-in off answers 409.

Current limits: an administrator works as its own account like everyone else (there is no "act as root" yet), so it sees only its own trash and only the files its own account may open. A virtual account gets 403 for `/` and for every folder outside its grants, and the web app opens at `/`, so such an account must go to a granted folder by its path; part 3 makes the web app open at the first grant.

### Not built yet

Not in this version: system sign-in by PAM or by `authorized_keys`, and acting as root (part 2, second step); screens and routes for accounts, keys, machine and source grants and ending sessions, grants for network sources, and the web app opening a virtual account at its first grant (part 3).
